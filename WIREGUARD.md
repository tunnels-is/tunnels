# WireGuard Integration

WireGuard is available as a parallel VPN protocol alongside the native tunnels protocol. Any standard WireGuard client (Android app, iOS app, desktop GUI) can connect without any custom software.

---

## Architecture

```
┌─────────────────────────────────────┐
│           Linux Server              │
│                                     │
│  ┌──────────────┐  ┌─────────────┐  │
│  │ tunnels      │  │  wg-server  │  │
│  │ (port 443)   │  │  (port 442) │  │
│  └──────┬───────┘  └──────┬──────┘  │
│         │  shared DB      │         │
│         └────────┬────────┘         │
│               controller            │
│            GET /v3/wg/peers         │
│                 (every 30s)         │
└─────────────────────────────────────┘
```

- **tunnels server** — handles the native hybrid post-quantum protocol and also acts as the auth controller
- **wg-server** — standalone binary that runs a userspace WireGuard device (wireguard-go), no kernel module required
- **wg-server polls the controller** every 30 seconds via `GET /v3/wg/peers`, diffs the result against currently configured peers, and adds/removes only what changed — active sessions are never torn down

Internet access uses kernel NAT: `ip_forward` + iptables `MASQUERADE`. There is no LAN routing by default (clients cannot reach each other unless you add a `wg0→wg0 FORWARD` rule manually).

## Configuration Reference

Config file is JSON or YAML (detected by extension). Generate a fresh config with a new private key:

```bash
./wg-server -config -configPath wg-config.json
```

| Field | Default | Description |
|---|---|---|
| `ControllerURL` | — | Base URL of the tunnels controller, e.g. `https://1.2.3.4:443` |
| `AdminAPIKey` | — | The `X-API-KEY` used to authenticate against `/v3/wg/peers` |
| `WireGuardPort` | `51820` | UDP port the WireGuard device listens on |
| `WireGuardPrivKey` | — | Base64 Curve25519 private key. Generated by `-config` flag |
| `WireGuardSubnet` | `10.1.0.0/16` | VPN subnet. `.1` is the server; clients start from `.2` |
| `WireGuardIface` | `wg0` | TUN device name |
| `InternetIface` | — | Outbound NIC for MASQUERADE, e.g. `eth0`, `enp1s0f0` |
| `SyncIntervalSecs` | `30` | How often to poll the controller for peer changes |
| `InsecureSkipVerify` | `false` | Skip TLS verification for the controller (for self-signed certs) |
| `LogLevel` | `debug` | `debug`, `info`, `warn`, or `error` |
| `LogJSON` | `false` | Emit logs as JSON |
| `Silent` | `false` | Disable all log output |

Example (`wg-config.json`):

```json
{
  "ControllerURL": "https://your-server-ip:443",
  "AdminAPIKey": "your-admin-api-key",
  "WireGuardPort": 51820,
  "WireGuardPrivKey": "<generated>",
  "WireGuardSubnet": "10.1.0.0/16",
  "WireGuardIface": "wg0",
  "InternetIface": "eth0",
  "SyncIntervalSecs": 30,
  "InsecureSkipVerify": false
}
```

## Build

```bash
# Build for local OS
cd wg-server && go build .

# Cross-compile for Linux amd64
cd wg-server && GOOS=linux GOARCH=amd64 go build -o wg-server-linux .
```

Requires `root` (or `CAP_NET_ADMIN`) to create TUN devices and modify iptables.

## Deployment

### 1. Generate config

```bash
./wg-server -config -configPath /opt/tunnels/wg-config.json
```

Edit the generated file and fill in `ControllerURL`, `AdminAPIKey`, and `InternetIface`. The private key is pre-generated; note the printed public key — you'll need it when registering devices.

### 2. Register the server public key in the controller

Set `Server.WireGuardPubKey` and `Server.WireGuardPort` on the server record in the DB so `POST /v3/wg/register` can return them to clients. With BoltDB these fields are updated via the admin API.

### 3. Run

```bash
./wg-server -configPath /opt/tunnels/wg-config.json
```

Flags:

| Flag | Description |
|---|---|
| `-config` | Generate default config file and exit |
| `-configPath` | Path to config file (default `./wg-config.json`) |
| `-logLevel` | Override log level |
| `-json` | JSON log output |
| `-silent` | Suppress all logs |
| `-source` | Include file/line in log output |
| `-version` | Print version and exit |

### 4. Supervisord unit (example)

```ini
[program:wg-server]
command=/opt/tunnels/wg-server -configPath /opt/tunnels/wg-config.json
autostart=true
autorestart=true
startretries=1000
user=root
directory=/opt/tunnels
redirect_stderr=true
stdout_logfile=/var/log/tunnels/wg-server.log
stdout_logfile_maxbytes=100MB
stdout_logfile_backups=10
```

```bash
supervisorctl reread && supervisorctl update
supervisorctl start wg-server
supervisorctl status
```

## iptables Rules

`wg-server` installs the following rules on startup and removes them on clean shutdown:

```bash
# Allow WireGuard UDP traffic in
iptables -A INPUT -p udp --dport <WireGuardPort> -j ACCEPT

# Allow forwarding from VPN to internet
iptables -A FORWARD -i wg0 -o <InternetIface> -j ACCEPT

# Allow return traffic back to VPN clients
iptables -A FORWARD -i <InternetIface> -o wg0 -m state --state RELATED,ESTABLISHED -j ACCEPT

# NAT client traffic out through the internet interface
iptables -t nat -A POSTROUTING -s <WireGuardSubnet> -o <InternetIface> -j MASQUERADE
```

The MASQUERADE rule is scoped to `WireGuardSubnet` so it does not interfere with the tunnels server's own traffic on the same machine.

These rules are **not persisted** across reboots independently — `wg-server` re-applies them each time it starts. If the process is not running, the rules will be absent. For production, ensure wg-server is managed by supervisord/systemd with `autostart=true`.

### Enabling peer-to-peer traffic

By default, clients are isolated and cannot reach each other. To allow client-to-client traffic, add this rule manually after wg-server has started:

```bash
iptables -A FORWARD -i wg0 -o wg0 -j ACCEPT
```

Remove it to re-isolate clients:

```bash
iptables -D FORWARD -i wg0 -o wg0 -j ACCEPT
```

## Controller API Endpoints

All endpoints are on the tunnels server (port 443). Authentication is either a session `DeviceToken` + `UID` (admin/manager only) or the `X-API-KEY` header.

### `POST /v3/wg/register`

Register a device's WireGuard public key and get an assigned VPN IP.

**Auth:** `DeviceToken` + `UID` (admin/manager) or `X-API-KEY`

**Request:**
```json
{
  "DeviceToken": "...",
  "UID": "<user-object-id>",
  "DeviceID": "<device-object-id>",
  "ServerID": "<server-object-id>",
  "PublicKeyB64": "<base64 Curve25519 public key>"
}
```

**Response:**
```json
{
  "AssignedIP":   "10.1.0.2",
  "ServerPubKey": "<base64 server public key>",
  "ServerIP":     "1.2.3.4",
  "ServerPort":   "51820",
  "Conf":         "[Interface]\n..."
}
```

The `Conf` field contains a ready-to-use `.conf` file (fill in `PrivateKey`).

---

### `DELETE /v3/wg/unregister`

Remove a device's WireGuard registration. The device will be removed from the wg-server within one sync interval.

**Auth:** `DeviceToken` + `UID` (admin/manager) or `X-API-KEY`

**Request:**
```json
{
  "DeviceToken": "...",
  "UID":         "<user-object-id>",
  "DeviceID":    "<device-object-id>"
}
```

---

### `GET /v3/wg/peers`

Returns all registered peers in UAPI-ready hex format. Used exclusively by `wg-server`.

**Auth:** `X-API-KEY` only

**Response:**
```json
{
  "Peers": [
    {
      "PublicKeyHex": "09ca5694...",
      "AllowedIP":    "10.1.0.2/32",
      "DeviceID":     "69a1dc61..."
    }
  ]
}
```

---

### `GET /v3/wg/config?serverID=<id>`

Returns WireGuard connection details for a server. Used by clients to build a config without registering a key first.

**Response:**
```json
{
  "WireGuardPubKey": "<base64>",
  "WireGuardPort":   "51820",
  "ServerIP":        "1.2.3.4"
}
```

## Adding a Client

### 1. Generate a keypair

```bash
# Using wg-tools (if installed)
wg genkey | tee privkey | wg pubkey > pubkey

# Or use the wg-qr tool (generates both + QR code)
cd cmd/wg-qr && go build .
```

### 2. Register the public key

```bash
curl -X POST https://<server>:443/v3/wg/register \
  -H "X-API-KEY: <AdminAPIKey>" \
  -H "Content-Type: application/json" \
  -d '{
    "DeviceID":     "<device-object-id>",
    "ServerID":     "<server-object-id>",
    "PublicKeyB64": "<base64 public key>"
  }'
```

The response includes `AssignedIP` and a pre-built `Conf` string.

### 3. Build the client config

```ini
[Interface]
PrivateKey = <your private key>
Address = 10.1.0.2/32
DNS = 1.1.1.1

[Peer]
PublicKey = <server public key>
Endpoint = <server-ip>:442
AllowedIPs = 0.0.0.0/0
PersistentKeepalive = 25
```

### 4. Generate a QR code (for mobile)

```bash
cd cmd/wg-qr && go build .
./wg-qr \
  -privkey  "<client private key>" \
  -address  "10.1.0.2/32" \
  -serverpub "<server public key>" \
  -endpoint  "<server-ip>:442" \
  -out       client.png
```

Prints the `.conf` to stdout, renders a QR code in the terminal, and saves a PNG to `-out`.

## IP Assignment

- Server always takes the **first host** in the subnet (e.g. `10.1.0.1` for `10.1.0.0/16`)
- Client IPs are assigned sequentially starting from `.2`
- Assignments are stored in `Device.WireGuardIP` in the database
- Reassignment is permanent: re-registering the same device reuses the existing IP

With a `/16` subnet (`10.1.0.0/16`) you have 65,533 usable client addresses.

## Troubleshooting

**Connection established but no internet**
- Confirm `ip_forward` is enabled: `cat /proc/sys/net/ipv4/ip_forward` → should be `1`
- Check iptables rules are present: `iptables -L FORWARD -n -v` and `iptables -t nat -L POSTROUTING -n -v`
- Confirm the INPUT rule exists for the WireGuard port: `iptables -L INPUT -n -v | grep <port>`

**Handshake never completes**
- The most common cause is a missing INPUT firewall rule for the WireGuard UDP port
- Check: `iptables -L INPUT -n | grep <port>`
- wg-server adds this automatically, but a pre-existing firewall with DROP INPUT policy will block it if wg-server isn't running

**Session drops every 30 seconds**
- This was caused by the old full-replace sync (`replace_peers=true`); the current diff-based sync preserves sessions across sync cycles

**"IPv4 packet with disallowed source address" in logs**
- Benign. WireGuard correctly drops packets whose inner source IP doesn't match the peer's `AllowedIP` (`10.x.x.x/32`). These typically come from the client briefly sending link-local or mDNS traffic right after a handshake

**Peer not appearing after registration**
- Peers are synced every `SyncIntervalSecs` (default 30s). Wait one full interval
- Verify the controller returns the peer: `curl -sk -H "X-API-KEY: ..." https://<server>/v3/wg/peers`

**Check logs**
```bash
# wg-server
tail -f /var/log/tunnels/wg-server.log

# tunnels controller
tail -f /var/log/tunnels/server.log

# supervisord
supervisorctl status
```
